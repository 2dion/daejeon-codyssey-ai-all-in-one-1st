# E1-3 · Mini NPU 시뮬레이터

> 미션: **AI가 계산하는 방식을 흉내 내는 작은 계산기 만들기**
> 입력 패턴과 필터를 같은 위치끼리 곱하고 모두 더하는 **MAC(Multiply-Accumulate)** 연산으로, 패턴이 십자가(Cross)인지 X인지 판정하는 Python 콘솔 프로그램이다.

## 2. 이 미션에서 다룬 개념

이 미션의 목표는 계산기 자체보다, 계산기를 만들면서 아래 여섯 가지를 이해하는 데 있다. 각 개념을 이 프로그램의 어디에서 확인했는지 함께 적었다.

### 2.1 MAC 연산과 AI에서의 중요성

**MAC은 "곱해서 누적해 더하는" 연산이고, 신경망 계산의 거의 전부가 이것이라서 AI 칩(NPU)은 MAC을 빠르게 하려고 만든 장치다.**

뉴런 하나는 입력마다 가중치를 곱해서 모두 더한다(w₁x₁ + w₂x₂ + … + b). 이 프로그램도 같다. 패턴이 입력, 필터가 가중치이고, 칸마다 곱해서 더한 값이 점수다([`mac()`](main.py#L122)). 실제 AI는 이 계산을 수십억 번 반복하므로, CPU처럼 하나씩 하지 않고 수천 개를 동시에 하는 NPU가 필요하다([6.3](#63-cpu와-npu에서-대규모-mac의-병목)). 이 프로그램의 이름이 "Mini NPU 시뮬레이터"인 것도 NPU가 하드웨어로 하는 MAC을 소프트웨어로 흉내 내고, 크기별 시간을 재서 왜 전용 하드웨어가 필요한지 직접 확인하기 때문이다.

### 2.2 곱하고 더해 유사도를 재는 원리

**0과 곱한 칸은 사라지고 패턴과 필터가 겹치는 칸만 점수에 남기 때문에, 점수가 클수록 모양이 비슷하다.**

3×3 X 패턴에 X 필터를 대면 겹치는 5칸이 더해져 5점, 십자가 필터를 대면 가운데 1칸만 겹쳐 1점이라 X로 판정한다. 다만 이 점수는 정규화되지 않은 내적이라, 필터 한 칸에 큰 가중치를 몰아 두면 겹치는 칸 수보다 가중치가 점수를 좌우한다. data.json의 FAIL 3건이 그 예다([5.1](#51-점수가-높을수록-비슷하다고-보는-이유), [7.1](#71-실패-원인-분석)).

### 2.3 키 규칙, 라벨 규칙과 정규화

**패턴 키에서 크기 N을 꺼내 같은 크기의 필터를 고르고, 라벨은 데이터가 들어오는 입구에서 한 번만 표준 이름으로 바꾼다.**

`size_13_2`에서 정규식으로 13을 꺼내 `filters[13]`을 찾는다([`PATTERN_KEY_RE`](main.py#L36)). 정답은 `+`, `x`로, 필터는 `cross`, `x`로 적혀 있어 그대로 비교하면 맞아도 FAIL이 되므로 [`normalize_label()`](main.py#L105)이 `Cross`, `X`로 통일한다. 모르는 라벨은 조용히 넘기지 않고 `[데이터/스키마]` 실패로 분류한다([4.2](#42-키에서-크기를-꺼내-필터-고르기), [4.3](#43-라벨-정규화를-함수로-분리한-이유)).

### 2.4 부동소수점 오차와 epsilon 비교

**`0.1` 같은 수는 2진수로 정확히 저장되지 않아 더할수록 오차가 쌓이므로, 두 점수의 차이가 1e-9보다 작으면 같은 점수로 본다.**

파이썬에서 `0.1 + 0.2 == 0.3`은 `False`다. data.json의 동점 3건은 수학적으로 같은 점수인데 컴퓨터 값은 1e-16 ~ 1e-15만큼 다르고, `>`로 비교하면 이 우연한 차이로 3건 모두 오답이 된다. epsilon을 너무 크게(예: 0.5) 잡으면 진짜로 다른 점수까지 동점이 되고, 너무 작게(예: 1e-20) 잡으면 오차를 걸러 내지 못한다. 1e-9는 누적 오차보다 훨씬 크고 실제 점수 차(0.1 이상)보다 훨씬 작다([5.3](#53-부동소수점-오차와-epsilon-비교)).

### 2.5 시간 측정과 O(N²)

**모든 칸에서 곱셈과 덧셈을 한 번씩 하니 N²번이고, 실제로 N이 2배가 될 때 시간이 약 4배가 됐다.**

측정은 `time.perf_counter()`로 MAC 호출 한 줄만 감싸고, 워밍업 1회를 버린 뒤 10회 평균을 낸다. 키보드 입력이나 `print`는 MAC보다 수천 배 느려서 섞으면 연산 시간이 보이지 않기 때문이다. N을 25에서 400까지 2배씩 늘리니 시간이 3.89, 3.96, 3.95, 4.12배로 늘었다([4.4](#44-시간-측정-구간), [7.2](#72-시간-복잡도-분석)).

### 2.6 실패 원인 세 갈래 진단

**실패를 데이터/스키마, 로직, 수치 비교 세 갈래로 나누고 앞에서부터 하나씩 배제한다. 이번 FAIL 3건은 마지막 갈래인 수치 비교(동점)였다.**

스키마 실패는 data.json에서 0건이었고, 같은 `mac()`으로 나머지 3건은 정답이었으며 실패 3건도 손으로 계산한 값과 같았다. 남은 원인은 두 점수 차가 epsilon 안에 드는 동점이다. 고치려면 판정 규칙이 아니라 데이터(필터 가중치)를 고쳐야 한다. 동점을 한쪽으로 몰아 PASS를 늘리면 동점은 FAIL로 센다는 요구사항을 어기고 데이터 문제를 숨기게 된다([7.1](#71-실패-원인-분석)).

## 4. 설계

### 4.1 MAC 계산 흐름

**입력, 검증, 정규화, 필터 선택, MAC, 비교, 출력을 함수 하나씩 맡겼고, MAC 함수는 검증이 끝난 두 Grid만 받아 숫자 하나를 돌려준다.**

```text
입력(콘솔 or JSON)
  → 검증 (Grid.from_rows, parse_row)          : 모양·숫자 확인, 실패 시 재입력 또는 케이스 FAIL
  → 라벨 정규화 (normalize_label)              : '+', 'x', 'cross' → Cross / X
  → 필터 선택 (PATTERN_KEY_RE로 N 추출 → filters[N])
  → MAC (mac)                                  : 위치별 곱셈 → 누적 합 → 점수(float)
  → 비교 (compare_scores, epsilon)             : A / B / 동점
  → 출력 (print_case, print_perf_table, 요약)
```

```python
def mac(pattern, filt):
    n = pattern.size
    a, b = pattern.cells, filt.cells
    total = 0.0
    for r in range(n):
        for c in range(n):
            total += a[r][c] * b[r][c]   # Multiply → Accumulate
    return total
```

합을 0으로 시작 → 모든 칸을 돌며 → 곱해서 더하고 → 돌려준다. 입력 → 위치별 곱셈 → 누적 합산 → 점수 반환의 네 단계가 코드 순서와 같고, NumPy 같은 벡터화 없이 반복문으로만 계산한다. MAC이 입력 방식과 분리되어 있으므로 모드 1, 2, 3이 모두 같은 `mac()`을 쓴다.

| 함수·클래스 | 하는 일 |
| --- | --- |
| [`Grid`](main.py#L50) | N×N 2차원 리스트를 감싼 데이터 구조. `get(r, c)`, `set(r, c, v)`로 위치 단위 저장·읽기, `from_rows()`로 검증 후 생성, `flatten()`으로 1차원 변환 |
| [`normalize_label(raw)`](main.py#L105) | 외부 표기를 표준 라벨 `Cross`, `X`로 바꾼다. 모르는 라벨이면 `ValueError` |
| [`mac(pattern, filt)`](main.py#L122) | 이중 `for` 반복문으로 누적. 크기가 다르면 `ValueError` |
| [`compare_scores(a, b)`](main.py#L151) | `abs(a - b) < 1e-9`면 `None`(동점), 아니면 큰 쪽 `'A'`/`'B'` |
| [`judge_labels(cross, x)`](main.py#L158) | 모드 2용. `Cross` / `X` / `UNDECIDED` |
| [`average_ms(func, *args)`](main.py#L169) | 워밍업 1회 후 10회 호출 시간을 재서 평균 ms |
| [`analyze_case(key, item, filters)`](main.py#L377) | 패턴 1개를 검증·판정하고 결과와 실패 원인 분류를 돌려준다. 예외를 밖으로 던지지 않는다. |

### 4.2 키에서 크기를 꺼내 필터 고르기

**정규식으로 키에서 N을 꺼내고, N을 키로 하는 딕셔너리에서 필터를 바로 찾은 뒤, 세 가지를 확인한다.**

```python
PATTERN_KEY_RE = re.compile(r"^size_(\d+)_(\d+)$")   # size_13_2 → N=13, idx=2
FILTER_KEY_RE  = re.compile(r"^size_(\d+)$")          # size_13   → N=13
filters = {13: {"Cross": Grid, "X": Grid}, ...}
```

이름 문자열을 조립(`"size_" + n`)하지 않고 숫자로 찾으므로 `size_013` 같은 표기 차이에도 덜 흔들린다. 매칭 후에는 세 가지를 차례로 확인한다.

1. 키의 N에 해당하는 필터가 있는가 (없으면 `size_7 필터가 없습니다.`)
2. 그 필터에 Cross와 X가 모두 있는가
3. 패턴 `input`의 실제 크기가 N과 같은가 (`크기 불일치: 키는 13x13, input은 5x5`)

하나라도 어긋나면 그 케이스만 FAIL로 기록하고 다음 케이스로 넘어간다. 필터 쪽도 같은 원칙으로, 키가 `size_N` 형식이 아니거나 실제 크기가 N과 다른 필터는 경고를 남기고 건너뛴다.

### 4.3 라벨 정규화를 함수로 분리한 이유

**같은 뜻을 다른 글자로 적은 데이터라 그대로 비교하면 맞는 판정도 FAIL이 되므로, 입구에서 한 번만 표준 라벨로 바꾸려고 분리했다.**

정답(`expected`)은 `'+'`, `'x'`이고 필터 키는 `'cross'`, `'x'`다. `'+' != 'cross'`라서 그대로 비교하면 맞는 판정도 FAIL이 된다.

```python
LABEL_ALIASES = {"+": "Cross", "cross": "Cross", "x": "X"}

def normalize_label(raw):
    key = raw.strip().lower()      # 'X', ' Cross ' 같은 대소문자·공백 차이도 흡수
    if key not in LABEL_ALIASES:
        raise ValueError(...)      # 모르는 라벨은 조용히 넘기지 않고 스키마 실패로
    return LABEL_ALIASES[key]
```

분리해서 얻는 장점은 세 가지다.

1. 규칙이 한 곳에 모인다. 새 표기(예: `'plus'`)가 생기면 표 한 줄만 고친다.
2. 판정 로직이 데이터 표기를 몰라도 된다. 판정 코드는 항상 표준 라벨 두 개만 다룬다.
3. 따로 시험할 수 있다. 정규화 실패가 판정 실패와 섞이지 않고 "데이터/스키마" 원인으로 분리된다.

### 4.4 시간 측정 구간

**`time.perf_counter()`로 MAC 호출 한 줄만 감싸고, 워밍업 1회를 버린 뒤 10회 평균을 낸다.**

```python
def average_ms(func, *args, repeat=10):
    func(*args)                         # 워밍업 1회, 측정 제외
    for _ in range(repeat):
        start = time.perf_counter()     # ← 측정 시작
        func(*args)                     # MAC 호출만
        total += time.perf_counter() - start   # ← 측정 끝
```

- 콘솔 입력, `json.load`, `Grid` 생성(검증), `print`는 모두 측정 구간 **밖**이다.
- `time.time()` 대신 `time.perf_counter()`를 쓴다. 짧은 구간을 재는 고해상도 단조 시계다.
- 첫 호출은 메모리 할당·캐시 비용이 섞여 튀므로 한 번 버리고 10회 평균을 낸다.

## 5. 핵심 원리

### 5.1 점수가 높을수록 비슷하다고 보는 이유

**곱셈에서 0인 칸은 사라지고 패턴과 필터가 함께 큰 칸만 남으니, 많이 겹칠수록 점수가 커진다. 수학적으로는 두 벡터의 내적이다.**

패턴은 모양이 있는 칸이 1, 없는 칸이 0이다. 필터는 자기 모양 칸에 큰 값을 둔다. 곱하면 패턴과 필터가 함께 큰 칸만 점수에 남고, 한쪽이라도 0인 칸은 사라진다. 그래서 겹치는 칸이 많을수록(그리고 그 칸의 가중치가 클수록) 합이 커진다. 내적은 두 벡터가 같은 방향일수록 커진다.

예: 3×3 X 패턴에 X 필터(대각선 1)를 대면 겹치는 5칸이 모두 더해져 5, 십자가 필터(가운데 행·열 1)를 대면 가운데 1칸만 겹쳐 1이다. 5 > 1이므로 X다.

한계도 있다. MAC 점수는 정규화되지 않은 값이라, 필터 한 칸에 큰 가중치를 몰아 두면 "겹치는 칸 수"보다 "가중치 크기"가 점수를 좌우한다. data.json의 FAIL 3건이 바로 이 경우다([7.1](#71-실패-원인-분석)). 필터에 음수 가중치가 있으면 점수가 음수일 수도 있지만, "더 큰 쪽이 더 비슷하다"는 규칙은 같다.

### 5.2 연산 횟수가 N²으로 느는 이유

**칸이 N×N개이고 칸마다 곱셈·덧셈을 한 번씩 하므로 N²이며, N을 2배로 하자 시간이 약 4배가 됐다.**

바깥 반복 N번 × 안쪽 반복 N번 = N²번이므로 O(N²)이다. 측정에서도 N을 2배씩 늘리면 시간이 3.89배, 3.96배, 3.95배, 4.12배로 꾸준히 약 4배가 됐다. 작은 N(3×3, 5×5)에서는 함수 호출 같은 고정 비용 때문에 배율이 4보다 작다. 측정 표와 해석은 [7.2 시간 복잡도 분석](#72-시간-복잡도-분석)에 있다.

### 5.3 부동소수점 오차와 epsilon 비교

**2진수로 정확히 표현되지 않는 수가 더해지며 오차가 쌓이기 때문에, 수학적으로 같은 점수가 끝자리만 다르게 나온다. 그래서 차이가 1e-9보다 작으면 같다고 본다.**

컴퓨터는 실수를 2진수로 저장한다. `0.1`은 2진수로 끝없이 이어지는 수(0.000110011…)라서 가장 가까운 근삿값으로 잘려 저장된다. 이 작은 오차가 덧셈마다 쌓여 `0.1`을 9번 더하면 `0.8999999999999999`가 된다.

`==`나 `>`로 비교하면 수학적으로 같은 두 점수 중 한쪽이 1e-16만큼 커서 **우연히** 이긴다.

```python
EPSILON = 1e-9
if abs(score_a - score_b) < EPSILON:   # 동점
```

1e-9는 이 데이터의 실제 점수 차(0.1 이상)보다 훨씬 작고, 누적 오차(1e-15 수준)보다는 훨씬 커서 둘을 확실히 가른다([`EPSILON`](main.py#L21)). data.json에서 epsilon 없이 `>`로 비교하면 동점 3건이 모두 **확신에 찬 오답**이 된다([7.1](#71-실패-원인-분석)의 표).

### 5.4 모드별 동점 처리 규칙

**모드 1은 정답이 없는 계산 도구라 "판정 불가"를 알려 주면 되고, 모드 2는 정답과 비교하는 테스트라 UNDECIDED를 FAIL로 세야 테스트가 의미를 가진다.**

| 모드 | 동점일 때 | 이유 |
| --- | --- | --- |
| 모드 1 | `판정 불가` 출력 | 정답이 없는 사용자 입력이다. 어느 쪽이라고 말할 근거가 없음을 그대로 알려 준다. |
| 모드 2 | `UNDECIDED` 출력, **FAIL로 집계** | `expected`는 항상 Cross 또는 X다. UNDECIDED는 둘 중 무엇과도 같지 않으므로 FAIL이다. 동점을 임의로 한쪽으로 몰아 PASS를 만들면 데이터 문제를 숨기게 된다. |

코드는 [`compare_scores()`](main.py#L151)(모드 1)와 [`judge_labels()`](main.py#L158)(모드 2)에 있다.

## 6. 확장과 한계

### 6.1 새 라벨이 추가된다면

**데이터가 들어오는 입구부터 고친다. 정규화 → 필터 로드 → 판정 일반화 → 출력 → 테스트 순서다.**

현재 코드는 라벨 두 개(Cross, X)를 전제로 한다. `'o'`를 받으면 지금은 `알 수 없는 라벨 'o'`로 스키마 FAIL을 낸다(broken.json의 size_5_4). 원 모양(Circle)을 세 번째 라벨로 지원한다면 다음 순서로 고친다.

1. **정규화.** `LABEL_CIRCLE = "Circle"`을 추가하고 [`LABEL_ALIASES`](main.py#L30)에 `"o": "Circle"`, `"circle": "Circle"`을 넣는다. 입구가 한 곳이라 여기만 고치면 이후 코드는 표준 라벨만 본다.
2. **필터 로드.** `load_filters()`가 `size_N`마다 Cross·X 두 개를 요구하는 부분을 "정의된 라벨 목록 전부"로 바꾼다. 원 필터가 없는 크기는 경고 후 건너뛴다.
3. **판정.** `judge_labels(cross, x)`의 두 값 비교를 `{라벨: 점수}` 딕셔너리로 일반화한다. 가장 큰 점수를 고르되, **1등과 2등의 차이가 epsilon보다 작으면** `UNDECIDED`다. 세 라벨이 모두 같은 경우도 같은 규칙으로 처리된다.
4. **출력.** `print_case()`가 라벨 수만큼 점수를 출력하게 한다. 판정 1건의 연산은 2N²에서 3N²이 되므로 성능 표의 의미(N² 경향)는 바뀌지 않는다.
5. **테스트.** expected가 `'o'`인 정상 케이스, 원과 다른 모양이 동점인 케이스, 원 필터가 없는 크기의 케이스를 추가한다. broken.json의 size_5_4는 더 이상 오류가 아니므로 기대 결과를 고친다.

입구(정규화)부터 고쳐야 뒤쪽 단계가 새 라벨을 표준 이름으로 받는다. 판정을 먼저 고치면 정규화되지 않은 `'o'`가 판정까지 흘러 들어가 원인을 찾기 어려워진다.

### 6.2 1000×1000 패턴을 처리한다면

**직접 재 보니 MAC 1회가 약 88 ms, 값이 제각각이면 한 장에 약 32 MB가 든다. 가장 먼저 반복을 C 쪽으로 내리면(`sum(map(...))`) 약 3.4배 빨라진다.**

이 저장소의 `main.py` 함수로 1000×1000 Cross 패턴과 X 필터를 직접 쟀다 (Python 3.10, 5회 평균, 2026-11-22).

| 방식 | MAC 1회 | 비고 |
| --- | --- | --- |
| 2D 이중 반복 `mac()` | 87.7 ms | 현재 기본 |
| 1D 반복 `mac_flat()` | 67.4 ms | 보너스 1, 약 23% 빠름 |
| `sum(map(operator.mul, a, b))` | 25.5 ms | 표준 라이브러리, 반복이 C 안에서 돈다 |

**시간.** 칸 100만 개라 MAC 1회가 약 88 ms, 판정 1건(필터 2개)이 약 175 ms다. 성능 표는 워밍업 1회 + 10회 반복이라 크기 하나에 약 2초가 걸린다. 한 건은 견딜 만하지만, 필터 수천 개를 이미지 곳곳에 반복하는 실제 AI 규모에서는 감당할 수 없다.

**메모리.** Python 리스트의 칸 하나는 포인터 8바이트이고, 서로 다른 실수 값이면 float 객체 24바이트가 따로 붙는다. 값이 제각각인 1000×1000은 한 장에 약 32 MB(실측 32.9 MB)이고, 패턴 1장 + 필터 2장이면 약 100 MB다. 2D와 1D를 둘 다 들고 있으면 포인터 배열이 한 벌 더 든다. JSON으로 받으면 문자열 파싱 중의 임시 메모리도 더해진다.

**최적화 순서.**

1. **반복을 C로 내린다.** `sum(map(operator.mul, a, b))`처럼 Python 바이트코드 반복을 없애는 것이 가장 효과가 크다(88 → 26 ms, 약 3.4배). 병목이 곱셈이 아니라 "칸마다 도는 인터프리터"라서다.
2. **1차원 연속 저장.** `array('d')`처럼 실수를 객체 없이 8바이트씩 붙여 저장하면 메모리가 약 1/4(32 MB → 8 MB)로 줄고 캐시 효율도 좋아진다.
3. **한 번 펴서 재사용.** `flatten()`을 측정마다 하지 않고 로드할 때 한 번만 하고, 2D 사본은 버린다.
4. **측정 반복 조정.** 큰 N에서는 반복 횟수를 줄이거나 총 시간 기준으로 멈춘다.
5. **미션 밖이라면** NumPy의 `dot`(C·SIMD 벡터 연산), 나아가 GPU·NPU로 넘긴다.

### 6.3 CPU와 NPU에서 대규모 MAC의 병목

**CPU는 한 칸씩 차례로 계산해서 계산 순서 자체가 병목이고, NPU는 수천 칸을 동시에 계산해서 데이터를 옮기는 메모리 대역폭이 병목이 된다.**

| 관점 | CPU (이 프로그램) | NPU |
| --- | --- | --- |
| 계산 방식 | 코어 하나가 곱셈·덧셈을 **한 번에 한 칸씩** 차례로 한다. N²칸이면 N²단계 | 수천 개의 MAC 유닛이 격자로 놓여 **수천 칸을 한 번에** 곱하고 더한다 |
| 병목 | **계산 순서 자체.** Python에서는 칸마다 인터프리터가 명령을 해석하는 비용이 곱셈보다 훨씬 크다(6.2의 3.4배 차이) | **데이터 이동.** 계산은 빠른데 메모리에서 가중치와 입력을 MAC 유닛까지 가져오는 속도(메모리 대역폭)가 따라가지 못한다 |
| 해결 방향 | 벡터화, C 반복, SIMD, 멀티코어 | 칩 안의 SRAM에 데이터를 두고 재사용, 낮은 정밀도(int8)로 옮길 양 줄이기, 배치 처리 |

MAC 하나하나는 서로 의존하지 않는다(어느 칸을 먼저 곱해도 결과가 같다). 그래서 병렬로 나누기 좋고, 이것이 AI 전용 하드웨어가 MAC 유닛을 대량으로 늘어놓는 이유다. 마지막 누적 합만은 순서가 있어서, 병렬 하드웨어는 부분 합을 나무 모양으로 모아 더한다. 이때 덧셈 순서가 바뀌므로 5.3의 부동소수점 오차가 결과 끝자리에 영향을 줄 수 있다. epsilon 비교는 병렬 환경에서 더 중요해진다.

## 7. 결과 리포트

### 7.1 실패 원인 분석

**결론: 6개 중 3개 FAIL이며, 세 건 모두 필터 가중치가 두 점수를 수학적으로 똑같이 만들도록 짜여 있어서 생긴 "동점"이다. 스키마나 MAC 로직의 오류는 아니다.**

실패를 세 갈래로 나눠 차례로 배제했다.

| 원인 갈래 | 확인한 것 | 결과 |
| --- | --- | --- |
| 데이터/스키마 | 모든 키가 `size_N_idx` 형식, 필터 3종 모두 Cross·X 존재, 모든 `input`이 N×N 숫자, `expected`가 `+`/`x`로 정규화 성공 | 문제 없음 (스키마 실패 0건) |
| 로직 | 같은 `mac()`로 나머지 3건은 정답. 실패 3건의 점수를 손으로 다시 계산해도 같은 값 (아래 표) | 문제 없음 |
| 수치 비교 | 세 건 모두 두 점수 차가 1e-16 ~ 1e-15. 수학적 값은 정확히 같음 | **원인** |

세 건이 왜 같은 점수가 되는지 필터를 직접 보면 드러난다. 각 필터가 "자기 모양"이 아닌 패턴을 만났을 때, 겹치는 한 칸(가운데)에 큰 가중치를 몰아 두었다.

| 케이스 | 패턴 | Cross 필터와 겹치는 칸 | X 필터와 겹치는 칸 | 수학적 점수 |
| --- | --- | --- | --- | --- |
| size_5_1 | X (1이 9칸) | 가운데 1칸 × 0.9 | 대각선 9칸 × 0.1 | 0.9 = 0.9 |
| size_13_2 | Cross (1이 25칸) | 25칸 × 0.3 | 가운데 1칸 × 7.5 | 7.5 = 7.5 |
| size_25_1 | X (1이 49칸) | 가운데 1칸 × 4.9 | 대각선 49칸 × 0.1 | 4.9 = 4.9 |

컴퓨터 계산에서는 `0.1`과 `0.3`이 2진수로 정확히 표현되지 않아, 칸 수만큼 더하는 동안 오차가 쌓인다. 한 칸짜리 쪽(`0.9`, `7.5`, `4.9`)은 한 번 곱해서 끝나므로 오차가 거의 없다. 그 결과 끝자리만 다른 값이 나온다.

epsilon 없이 `>`로 비교했다면 어떻게 되는지도 같은 점수로 확인했다.

| 케이스 | 단순 `>` 비교 판정 | expected | 결과 |
| --- | --- | --- | --- |
| size_5_1 | Cross (0.9 > 0.8999999999999999) | X | FAIL (오답) |
| size_13_2 | X (7.5 > 7.499999999999997) | Cross | FAIL (오답) |
| size_25_1 | Cross (4.9 > 4.899999999999999) | X | FAIL (오답) |

단순 비교에서도 똑같이 3건이 틀린다. 차이는 **틀리는 방식**이다. 단순 비교는 덧셈 순서 같은 우연에 따라 확신에 찬 오답을 내고, 원인이 어디 있는지 알려 주지 않는다. epsilon 정책은 "이 필터로는 구분할 수 없다"는 사실을 `UNDECIDED`로 드러내고 실패 원인을 `[수치 비교]`로 분류해 준다. 이번 FAIL 3건은 숨겨진 버그가 아니라 **필터 설계(데이터)의 한계를 정직하게 보고한 결과**다.

개선하려면 판정 규칙이 아니라 데이터를 고쳐야 한다. 예를 들어 필터의 가운데 칸에 다른 칸과 같은 가중치를 주거나(`size_13` X 필터 가운데 7.5 → 0.3), Cross·X 필터의 가중치 합을 맞추면 이 패턴들은 정답 쪽 점수가 확실히 커진다. 다만 미션은 주어진 `data.json`을 그대로 판정하는 것이므로 데이터는 바꾸지 않았다. 동점을 한쪽으로 몰아 PASS를 늘리는 처리도 요구사항(동점은 FAIL로 집계)에 어긋나서 하지 않았다.

스키마·크기 문제가 섞인 데이터([samples/broken.json](samples/broken.json))에서는 실패가 `[데이터/스키마]`로 따로 분류된다([3.3](#33-오류-입력-처리)). 원인 분류가 세 갈래로 나뉘어 출력되므로 실패 목록만 보고도 데이터를 고칠지, 코드를 고칠지, 비교 기준을 고칠지 정할 수 있다.

### 7.2 시간 복잡도 분석

**MAC은 O(N²)이고, N을 2배씩 늘린 측정에서 시간이 꾸준히 약 4배가 되어 이를 확인했다.**

N×N 패턴의 MAC은 모든 칸을 한 번씩 방문해 곱셈 1번, 덧셈 1번을 한다. 바깥 반복 N번 × 안쪽 반복 N번 = **N²번**이다. 그래서 시간 복잡도는 **O(N²)**, 패턴 한 변이 2배가 되면 연산은 4배가 된다. 판정 1건에는 필터 2개(Cross, X)를 쓰므로 2N²번이지만, 상수 배는 Big-O에서 지운다.

미션 크기의 측정값([3.4](#34-성능-분석-표))을 연산 횟수와 나란히 놓으면 다음과 같다.

| 구간 | 연산 횟수 배율 (N²) | 시간 배율 (2D) | 칸당 시간 |
| --- | --- | --- | --- |
| 3×3 → 5×5 | 2.8배 | 2.0배 | 0.10 → 0.072 µs |
| 5×5 → 13×13 | 6.8배 | 5.1배 | 0.072 → 0.054 µs |
| 13×13 → 25×25 | 3.7배 | 3.4배 | 0.054 → 0.051 µs |

작은 N에서는 시간 배율이 N² 배율보다 작다. 함수 호출, 변수 준비, `range` 생성 같은 **크기와 무관한 고정 비용**이 전체에서 차지하는 비율이 커서다. 3×3은 연산 자체가 1 µs도 안 되어 시계 해상도와 OS 잡음의 영향도 받는다. N이 커질수록 칸당 시간이 일정한 값으로 수렴하면서 시간이 N²에 비례해 간다.

경향을 분명히 보려고 [samples/perf_sweep.py](samples/perf_sweep.py)로 N을 2배씩 늘려 측정했다 (RUN_LOG 6장).

| N | N² | 2D 평균(ms) | 직전 대비 | 1D 평균(ms) |
| --- | --- | --- | --- | --- |
| 25 | 625 | 0.0315 | - | 0.0252 |
| 50 | 2,500 | 0.1225 | 3.89배 | 0.0988 |
| 100 | 10,000 | 0.4850 | 3.96배 | 0.3988 |
| 200 | 40,000 | 1.9135 | 3.95배 | 1.5915 |
| 400 | 160,000 | 7.8851 | 4.12배 | 6.3568 |

N이 2배일 때 시간이 꾸준히 약 4배(= 2²)가 된다. 이것이 측정으로 본 O(N²)의 근거다. 공간 복잡도도 O(N²)이다. 패턴과 필터 두 개를 N×N으로 저장해야 하고, MAC 자체는 누적값 `total` 하나만 쓰므로 추가 메모리는 O(1)이다. 1000×1000에서의 실측과 최적화는 [6.2](#62-10001000-패턴을-처리한다면)에 있다.

## 8. 보너스 과제

**1. 1차원 배열 최적화.** [`Grid.flatten()`](main.py#L87)으로 N×N을 길이 N²의 리스트로 펴고 [`mac_flat()`](main.py#L137)에서 인덱스 하나(`i`)로 접근한다. 2D는 `a[r][c]`마다 행 리스트를 한 번 더 찾아야 하지만 1D는 한 번이면 된다. 같은 입력·같은 10회 반복으로 잰 결과, 모든 크기에서 1D가 약 17~39% 빨랐다(예: 400×400에서 7.89 ms → 6.36 ms). 복잡도는 둘 다 O(N²)이고 바뀐 것은 칸당 상수 비용이다. 모드 2와 모드 3의 성능 표에 `1D 평균(ms)` 열로 함께 출력한다.

**2. 패턴 생성기.** [`make_cross(n)`](main.py#L187)(가운데 행·열), [`make_x(n)`](main.py#L197)(두 대각선)이 N×N 패턴을 만든다. 모드 3에서 N을 받아 패턴을 보여 주고, 생성한 패턴끼리 MAC으로 자기 판정(Cross 패턴 → Cross)을 확인한 뒤 성능 표를 출력한다(RUN_LOG 5장). 모드 2 성능 표의 3×3 행과 `samples/perf_sweep.py`의 큰 N 측정도 이 생성기를 재활용한다.
