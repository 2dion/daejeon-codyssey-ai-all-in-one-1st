## 3. 구현 요약

### 3.1 전체 구조

```text
입력(콘솔 or JSON)
  → 검증 (Grid.from_rows, parse_row)          : 모양·숫자 확인, 실패 시 재입력 또는 케이스 FAIL
  → 라벨 정규화 (normalize_label)              : '+', 'x', 'cross' → Cross / X
  → 필터 선택 (PATTERN_KEY_RE로 N 추출 → filters[N])
  → MAC (mac)                                  : 위치별 곱셈 → 누적 합 → 점수(float)
  → 비교 (compare_scores, epsilon)             : A / B / 동점
  → 출력 (print_case, print_perf_table, 요약)
```

| 함수·클래스 | 하는 일 |
| --- | --- |
| `Grid` | N×N 2차원 리스트를 감싼 데이터 구조. `get(r, c)`, `set(r, c, v)`로 위치 단위 저장·읽기, `from_rows()`로 검증 후 생성, `flatten()`으로 1차원 변환 |
| `normalize_label(raw)` | 외부 표기를 표준 라벨 `Cross`, `X`로 바꾼다. 모르는 라벨이면 `ValueError` |
| `mac(pattern, filt)` | 이중 `for` 반복문으로 `total += a[r][c] * b[r][c]` 누적. 크기가 다르면 `ValueError` |
| `compare_scores(a, b)` | `abs(a - b) < 1e-9`면 `None`(동점), 아니면 큰 쪽 `'A'`/`'B'` |
| `judge_labels(cross, x)` | 모드 2용. `Cross` / `X` / `UNDECIDED` |
| `average_ms(func, *args)` | 워밍업 1회 후 10회 호출 시간을 `time.perf_counter()`로 재서 평균 ms |
| `analyze_case(key, item, filters)` | 패턴 1개를 검증·판정하고 결과와 실패 원인 분류를 돌려준다. 예외를 밖으로 던지지 않는다. |

### 3.2 라벨 정규화

`data.json`은 같은 뜻을 다른 글자로 적는다. 정답(`expected`)은 `'+'`, `'x'`이고 필터 키는 `'cross'`, `'x'`다. 그대로 비교하면 `'+' != 'cross'`라서 맞는 판정도 FAIL이 된다.

```python
LABEL_ALIASES = {"+": "Cross", "cross": "Cross", "x": "X"}

def normalize_label(raw):
    key = raw.strip().lower()      # 'X', ' Cross ' 같은 대소문자·공백 차이도 흡수
    if key not in LABEL_ALIASES:
        raise ValueError(...)      # 모르는 라벨은 조용히 넘기지 않고 스키마 실패로
    return LABEL_ALIASES[key]
```

데이터가 들어오는 입구(필터 로드, expected 읽기)에서 한 번만 바꾸고, 그 뒤로는 출력과 PASS/FAIL 비교 모두 `Cross`/`X`만 쓴다. 별도 함수로 분리한 이유는 세 가지다.

1. 규칙이 한 곳에 모인다. 새 표기(예: `'X'`, `'plus'`)가 생기면 표 한 줄만 고친다.
2. 판정 로직이 데이터 표기를 몰라도 된다. 판정 코드는 항상 표준 라벨 두 개만 다룬다.
3. 따로 시험할 수 있다. 정규화 실패가 판정 실패와 섞이지 않고 "데이터/스키마" 원인으로 분리된다.

### 3.3 키에서 N 추출과 필터 매칭

```python
PATTERN_KEY_RE = re.compile(r"^size_(\d+)_(\d+)$")   # size_13_2 → N=13, idx=2
FILTER_KEY_RE  = re.compile(r"^size_(\d+)$")          # size_13   → N=13
```

필터는 `{13: {"Cross": Grid, "X": Grid}}`처럼 **크기 N을 키로 하는 딕셔너리**에 담는다. 패턴 키에서 N을 꺼내 `filters[N]`으로 바로 찾는다. 이름 문자열을 조립(`"size_" + n`)하지 않고 숫자로 찾으므로 `size_013` 같은 표기 차이에도 덜 흔들린다. 매칭 후에는 세 가지를 차례로 확인한다.

1. 키의 N에 해당하는 필터가 있는가 (없으면 `size_7 필터가 없습니다.`)
2. 그 필터에 Cross와 X가 모두 있는가
3. 패턴 `input`의 실제 크기가 N과 같은가 (`크기 불일치: 키는 13x13, input은 5x5`)

하나라도 어긋나면 그 케이스만 FAIL로 기록하고 다음 케이스로 넘어간다. 필터 쪽도 같은 원칙으로, 키가 `size_N` 형식이 아니거나 실제 크기가 N과 다른 필터는 경고를 남기고 건너뛴다.

### 3.4 MAC 연산

```python
def mac(pattern, filt):
    n = pattern.size
    a, b = pattern.cells, filt.cells
    total = 0.0
    for r in range(n):
        for c in range(n):
            total += a[r][c] * b[r][c]   # Multiply → Accumulate
    return total
```

입력 → 위치별 곱셈 → 누적 합산 → 점수 반환의 네 단계가 코드 순서와 같다. NumPy 같은 벡터화 없이 반복문으로만 계산한다. 필터 값이 패턴의 1인 칸과 많이 겹칠수록 더해지는 항이 많아지므로, **점수가 클수록 패턴이 그 필터 모양과 비슷하다**고 본다.

### 3.5 점수 비교 정책 (epsilon)

```python
EPSILON = 1e-9
if abs(score_a - score_b) < EPSILON:   # 동점
```

`0.1`은 2진수로 정확히 표현되지 않아 `0.1`을 9번 더하면 `0.8999999999999999`가 된다. `==`나 `>`로 비교하면 수학적으로 같은 두 점수 중 한쪽이 1e-16만큼 커서 **우연히** 이긴다. 그래서 차이가 1e-9보다 작으면 같은 점수로 본다. 1e-9는 이 데이터의 실제 점수 차(0.1 이상)보다 훨씬 작고 누적 오차(1e-15 수준)보다는 훨씬 커서 둘을 확실히 가른다.

| 모드 | 동점일 때 | 이유 |
| --- | --- | --- |
| 모드 1 | `판정 불가` 출력 | 정답이 없는 사용자 입력이다. 어느 쪽이라고 말할 근거가 없음을 그대로 알려 준다. |
| 모드 2 | `UNDECIDED` 출력, **FAIL로 집계** | `expected`는 항상 Cross 또는 X다. UNDECIDED는 둘 중 무엇과도 같지 않으므로 FAIL이다. 동점을 임의로 한쪽으로 몰아 PASS를 만들면 데이터 문제를 숨기게 된다. |

### 3.6 시간 측정 경계

```python
def average_ms(func, *args, repeat=10):
    func(*args)                         # 워밍업 1회, 측정 제외
    for _ in range(repeat):
        start = time.perf_counter()     # ← 측정 시작
        func(*args)                     # MAC 호출만
        total += time.perf_counter() - start   # ← 측정 끝
```

- 콘솔 입력, `json.load`, `Grid` 생성(검증), `print`는 모두 측정 구간 **밖**에서 끝낸 뒤 호출한다.
- `time.time()` 대신 `time.perf_counter()`를 쓴다. 짧은 구간을 재는 고해상도 단조 시계다.
- 첫 호출은 메모리 할당·캐시 비용이 섞여 튀므로 한 번 버리고 10회 평균을 낸다.

## 5. 결과 리포트

### 5.1 실패 원인 분석

**결론: 6개 중 3개 FAIL이며, 세 건 모두 필터 가중치가 두 점수를 수학적으로 똑같이 만들도록 짜여 있어서 생긴 "동점"이다. 스키마나 MAC 로직의 오류는 아니다.**

실패를 세 갈래로 나눠 차례로 배제했다.

| 원인 갈래 | 확인한 것 | 결과 |
| --- | --- | --- |
| 데이터/스키마 | 모든 키가 `size_N_idx` 형식, 필터 3종 모두 Cross·X 존재, 모든 `input`이 N×N 숫자, `expected`가 `+`/`x`로 정규화 성공 | 문제 없음 (스키마 실패 0건) |
| 로직 | 같은 `mac()`로 나머지 3건은 정답. 실패 3건의 점수를 손으로 다시 계산해도 같은 값 (아래 표) | 문제 없음 |
| 수치 비교 | 세 건 모두 두 점수 차가 1e-16 ~ 1e-15. 수학적 값은 정확히 같음 | **원인** |

세 건이 왜 같은 점수가 되는지 필터를 직접 보면 드러난다. 각 필터가 "자기 모양"이 아닌 패턴을 만났을 때, 겹치는 한 칸(가운데)에 큰 가중치를 몰아 두었다.

| 케이스 | 패턴 | Cross 필터와 겹치는 칸 | X 필터와 겹치는 칸 | 수학적 점수 |
| --- | --- | --- | --- | --- |
| size_5_1 | X (1이 9칸) | 가운데 1칸 × 0.9 | 대각선 9칸 × 0.1 | 0.9 = 0.9 |
| size_13_2 | Cross (1이 25칸) | 25칸 × 0.3 | 가운데 1칸 × 7.5 | 7.5 = 7.5 |
| size_25_1 | X (1이 49칸) | 가운데 1칸 × 4.9 | 대각선 49칸 × 0.1 | 4.9 = 4.9 |

컴퓨터 계산에서는 `0.1`과 `0.3`이 2진수로 정확히 표현되지 않아, 칸 수만큼 더하는 동안 오차가 쌓인다. 한 칸짜리 쪽(`0.9`, `7.5`, `4.9`)은 한 번 곱해서 끝나므로 오차가 거의 없다. 그 결과 끝자리만 다른 값이 나온다.

epsilon 없이 `>`로 비교했다면 어떻게 되는지도 같은 점수로 확인했다.

| 케이스 | 단순 `>` 비교 판정 | expected | 결과 |
| --- | --- | --- | --- |
| size_5_1 | Cross (0.9 > 0.8999999999999999) | X | FAIL (오답) |
| size_13_2 | X (7.5 > 7.499999999999997) | Cross | FAIL (오답) |
| size_25_1 | Cross (4.9 > 4.899999999999999) | X | FAIL (오답) |

단순 비교에서도 똑같이 3건이 틀린다. 차이는 **틀리는 방식**이다. 단순 비교는 덧셈 순서 같은 우연에 따라 확신에 찬 오답을 내고, 원인이 어디 있는지 알려 주지 않는다. epsilon 정책은 "이 필터로는 구분할 수 없다"는 사실을 `UNDECIDED`로 드러내고 실패 원인을 `[수치 비교]`로 분류해 준다. 이번 FAIL 3건은 숨겨진 버그가 아니라 **필터 설계(데이터)의 한계를 정직하게 보고한 결과**다.

개선하려면 판정 규칙이 아니라 데이터를 고쳐야 한다. 예를 들어 필터의 가운데 칸에 다른 칸과 같은 가중치를 주거나(`size_13` X 필터 가운데 7.5 → 0.3), Cross·X 필터의 가중치 합을 맞추면 이 패턴들은 정답 쪽 점수가 확실히 커진다. 다만 미션은 주어진 `data.json`을 그대로 판정하는 것이므로 데이터는 바꾸지 않았다. 동점을 한쪽으로 몰아 PASS를 늘리는 처리도 요구사항(동점은 FAIL로 집계)에 어긋나서 하지 않았다.

참고로 스키마·크기 문제가 섞인 데이터([samples/broken.json](samples/broken.json))에서는 실패가 `[데이터/스키마]`로 따로 분류된다([6장](#6-오류-입력-검증)). 원인 분류가 세 갈래로 나뉘어 출력되므로 실패 목록만 보고도 데이터를 고칠지, 코드를 고칠지, 비교 기준을 고칠지 정할 수 있다.

### 5.2 시간 복잡도 분석

N×N 패턴의 MAC은 모든 칸을 한 번씩 방문해 곱셈 1번, 덧셈 1번을 한다. 바깥 반복 N번 × 안쪽 반복 N번 = **N²번**이다. 그래서 시간 복잡도는 **O(N²)**, 패턴 한 변이 2배가 되면 연산은 4배가 된다. 판정 1건에는 필터 2개(Cross, X)를 쓰므로 2N²번이지만, 상수 배는 Big-O에서 지운다.

미션 크기의 측정값(위 성능 표)을 연산 횟수와 나란히 놓으면 다음과 같다.

| 구간 | 연산 횟수 배율 (N²) | 시간 배율 (2D) | 칸당 시간 |
| --- | --- | --- | --- |
| 3×3 → 5×5 | 2.8배 | 2.0배 | 0.10 → 0.072 µs |
| 5×5 → 13×13 | 6.8배 | 5.1배 | 0.072 → 0.054 µs |
| 13×13 → 25×25 | 3.7배 | 3.4배 | 0.054 → 0.051 µs |

작은 N에서는 시간 배율이 N² 배율보다 작다. 함수 호출, 변수 준비, `range` 생성 같은 **크기와 무관한 고정 비용**이 전체에서 차지하는 비율이 커서다. 3×3은 연산 자체가 1 µs도 안 되어 시계 해상도와 OS 잡음의 영향도 받는다. N이 커질수록 칸당 시간이 약 0.05 µs로 수렴하면서 시간이 N²에 비례해 간다.

경향을 분명히 보려고 [samples/perf_sweep.py](samples/perf_sweep.py)로 N을 2배씩 늘려 측정했다.

| N | N² | 2D 평균(ms) | 직전 대비 | 1D 평균(ms) |
| --- | --- | --- | --- | --- |
| 25 | 625 | 0.0315 | - | 0.0252 |
| 50 | 2,500 | 0.1225 | 3.89배 | 0.0988 |
| 100 | 10,000 | 0.4850 | 3.96배 | 0.3988 |
| 200 | 40,000 | 1.9135 | 3.95배 | 1.5915 |
| 400 | 160,000 | 7.8851 | 4.12배 | 6.3568 |

N이 2배일 때 시간이 꾸준히 약 4배(= 2²)가 된다. 이것이 측정으로 본 O(N²)의 근거다. 공간 복잡도도 O(N²)이다. 패턴과 필터 두 개를 N×N으로 저장해야 하고, MAC 자체는 누적값 `total` 하나만 쓰므로 추가 메모리는 O(1)이다.

이 숫자로 1000×1000을 어림하면 칸 100만 개 × 0.05 µs ≈ 50 ms(필터 2개면 약 100 ms)다. 한 번은 견딜 만하지만, 실제 AI처럼 필터 수천 개 × 이미지 위 수많은 위치에 반복하면 순수 Python 반복문은 감당할 수 없다. 그래서 같은 곱셈·덧셈을 한꺼번에 처리하는 병렬 하드웨어(GPU, NPU)가 필요해진다.

## 8. 보너스 과제

**1. 1차원 배열 최적화.** `Grid.flatten()`으로 N×N을 길이 N²의 리스트로 펴고 `mac_flat()`에서 인덱스 하나(`i`)로 접근한다. 2D는 `a[r][c]`마다 행 리스트를 한 번 더 찾아야 하지만 1D는 한 번이면 된다. 같은 입력·같은 10회 반복으로 잰 결과, 모든 크기에서 1D가 약 17~39% 빨랐다(예: 400×400에서 7.89 ms → 6.36 ms). 복잡도는 둘 다 O(N²)이고 바뀐 것은 칸당 상수 비용이다. 모드 2와 모드 3의 성능 표에 `1D 평균(ms)` 열로 함께 출력한다.

**2. 패턴 생성기.** `make_cross(n)`(가운데 행·열), `make_x(n)`(두 대각선)이 N×N 패턴을 만든다. 모드 3에서 N을 받아 패턴을 보여 주고, 생성한 패턴끼리 MAC으로 자기 판정(Cross 패턴 → Cross)을 확인한 뒤 성능 표를 출력한다. 모드 2 성능 표의 3×3 행과 `samples/perf_sweep.py`의 큰 N 측정도 이 생성기를 재활용한다.
