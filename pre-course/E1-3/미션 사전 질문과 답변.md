### 01. MAC 연산의 공식적인 정의가 있나?

있다. 디지털 신호 처리(DSP)와 컴퓨터 구조에서 쓰는 이름으로, **곱한 값을 누산기(accumulator)에 더하는 한 단계 연산**을 말한다.

```text
a ← a + (b × c)
```

이 한 단계를 하는 하드웨어 회로를 MAC 유닛(MAC unit)이라 부른다. 이 미션의 MAC 점수는 이 단계를 N²번 반복한 결과이고, 수학적으로는 두 배열을 길게 편 벡터의 **내적(dot product)** 과 같다.

```text
점수 = Σ (패턴[i][j] × 필터[i][j])   (모든 i, j)
```

현대 CPU에는 곱셈과 덧셈을 반올림 한 번으로 묶어 처리하는 FMA(Fused Multiply-Add) 명령이 있어서, MAC은 하드웨어 수준에서도 독립된 기본 연산으로 취급된다.

<a id="q02"></a>
### 02. 패턴과 필터의 유사도를 재는 다른 방법은?

MAC(내적) 말고도 여러 방법이 있다. 무엇을 "닮았다"고 볼지에 따라 고른다.

| 방법 | 계산 | 특징 |
| --- | --- | --- |
| 내적 (MAC) | Σ a·b | 가장 단순하고 빠르다. 값의 크기(밝기, 가중치 합)에 영향을 받는다. |
| 코사인 유사도 | Σ a·b / (‖a‖·‖b‖) | 내적을 두 벡터 길이로 나눠 **방향**만 비교한다. 크기 차이를 없앤다. |
| 유클리드 거리 | √Σ (a−b)² | 작을수록 닮음. 칸별 차이를 그대로 본다. |
| 해밍 거리 | 다른 칸의 개수 | 0/1 이진 패턴에 적합하다. |
| 정규화 상호상관(NCC) | 평균을 뺀 뒤 코사인 유사도 | 밝기·대비가 달라도 모양이 같으면 높게 나온다. 템플릿 매칭에서 많이 쓴다. |

이 미션의 `data.json`에서 동점이 난 이유도 여기 있다. 내적은 필터 가중치 합의 영향을 그대로 받는데, 필터 하나의 가운데 칸에 큰 값을 몰아 넣어 점수를 인위적으로 맞춰 두었다. 코사인 유사도처럼 크기를 정규화했다면 결과가 달랐을 것이다. 하지만 미션 요구사항은 MAC이므로 MAC으로 판정했다.

<a id="q03"></a>
### 03. MAC이 AI에서 특히 중요한 이유는?

신경망 계산의 거의 전부가 MAC이기 때문이다.

- **뉴런 하나**: 입력 x에 가중치 w를 곱해 모두 더하고(= MAC) 활성화 함수를 씌운다. `y = f(Σ wᵢxᵢ + b)`
- **합성곱(CNN)**: 이 미션처럼 필터를 이미지 위에서 한 칸씩 옮기며 위치마다 MAC을 한다.
- **완전연결층, 행렬곱**: 행렬곱 C = A × B의 각 칸이 행과 열의 내적, 즉 MAC 묶음이다.

그래서 AI 모델의 계산량은 흔히 MAC 횟수(또는 FLOPs, MAC 1번 ≈ 2 FLOPs)로 센다. 칩 성능도 "초당 몇 조 번 연산(TOPS)"으로 표시하는데, 그 대부분이 MAC이다. MAC을 빨리, 많이, 적은 전력으로 하는 것이 곧 AI 하드웨어의 성능이다.

<a id="q04"></a>
### 04. Transformer(Attention Is All You Need)와도 관련 있나?

깊게 관련 있다. Transformer의 핵심인 어텐션은 **"어떤 단어가 어떤 단어와 얼마나 비슷한가"** 를 내적으로 잰다.

```text
Attention(Q, K, V) = softmax(Q·Kᵀ / √d) · V
```

- `Q·Kᵀ`: 질의(Query) 벡터와 키(Key) 벡터의 내적 = 유사도 점수. 이 미션의 "패턴과 필터의 MAC 점수"와 같은 발상이다.
- `√d`로 나누는 것: 차원이 커지면 내적 값이 커져 softmax가 한쪽으로 쏠리므로 크기를 맞춘다(일종의 정규화).
- `· V`: 점수로 가중합을 구하는 것도 MAC이다.

즉 "곱해서 더한 값이 크면 닮았다"는 이 미션의 원리가 대형 언어 모델까지 그대로 이어진다. 다른 점은 필터가 사람이 정한 값이 아니라 학습으로 정해진다는 것이다.

<a id="q05"></a>
### 05. 사람도 병렬로 계산할 수 있나? 시각은 병렬 처리인가?

**의식적인 계산**(암산, 글 읽기)은 대체로 직렬이다. 주의(attention)를 한 번에 한 과제에만 깊게 쓸 수 있어서, 두 가지를 동시에 한다고 느낄 때는 대부분 빠르게 번갈아 전환하는 것이다. 질문에서 짐작한 "전환이 빠른 것"이 맞다.

반면 **시각은 대규모 병렬 처리**다. 망막에는 약 1억 개 넘는 광수용체가 있고, 각 세포가 동시에 빛을 받아 신호를 낸다. 1차 시각 피질의 뉴런들은 각자 시야의 작은 영역에서 특정 방향의 선(가로, 세로, 대각선)에 반응하는데, 이것이 바로 작은 필터를 이미지 곳곳에 동시에 대는 것과 비슷하다. CNN은 실제로 이 구조에서 영감을 받았다. 그래서 사람은 십자가와 X를 "계산 없이" 순간적으로 구별한다. 계산을 안 하는 게 아니라 병렬로 아주 빨리 해서 의식에 안 잡히는 것이다.

<a id="q06"></a>
### 06. CPU, GPU, NPU는 각각 무엇인가?

| 구분 | 설계 목표 | 코어 | 잘하는 일 |
| --- | --- | --- | --- |
| CPU (Central Processing Unit) | 어떤 프로그램이든 빠르게 한 흐름씩 | 강력한 코어 수 개~수십 개 | 분기·조건이 많은 일반 프로그램, 운영체제, 순서가 중요한 작업 |
| GPU (Graphics Processing Unit) | 같은 계산을 엄청나게 많은 데이터에 동시에 | 단순한 코어 수천 개 | 그래픽(픽셀·정점 계산), 행렬 연산, AI 학습 |
| NPU (Neural Processing Unit) | 신경망 연산(MAC)만 최소 전력으로 | MAC 유닛 배열 | AI 추론(얼굴 인식, 음성 인식 등), 특히 휴대폰·노트북 |

CPU는 코어 하나하나가 똑똑하다(분기 예측, 큰 캐시, 비순차 실행). GPU와 NPU는 하나하나는 단순하지만 수가 압도적으로 많다.

<a id="q07"></a>
### 07. 병렬 CPU나 아주 빠른 CPU로는 부족한가?

요즘 CPU도 멀티코어이고 SIMD(한 명령으로 여러 데이터를 계산하는 명령, 예: AVX)로 어느 정도 병렬 계산을 한다. 그래도 부족한 이유는 두 가지다.

1. **클럭을 더 올릴 수 없다.** 2000년대 중반부터 발열과 전력 때문에 CPU 클럭은 대략 3~5 GHz에서 멈췄다. "아주 빠르게 직렬로" 하는 길이 물리적으로 막혔다.
2. **CPU 면적의 대부분이 계산이 아닌 곳에 쓰인다.** 캐시, 분기 예측, 명령 해석 같은 범용성을 위한 회로가 크다. MAC처럼 단순한 계산을 수십억 번 하는 데는 이 회로가 필요 없고, 그 면적에 계산기를 더 넣는 편이 낫다.

비유하면, CPU는 뭐든 잘하는 전문가 몇 명이고 GPU/NPU는 덧셈·곱셈만 하는 계산원 수천 명이다. 수억 번의 단순 곱셈 덧셈은 계산원 쪽이 압도적으로 빠르다.

<a id="q08"></a>
### 08. GPU도 병렬인데 NPU를 따로 만든 이유는?

짐작대로 "병렬"만으로 보면 GPU로 충분하다. 실제로 AI 학습은 대부분 GPU로 한다. NPU를 따로 만든 이유는 **더 좁게 특화해서 효율을 높이기 위해서**다.

- **연산 단위**: GPU는 범용 병렬 코어라서 그래픽용 기능(텍스처, 래스터라이저 등)과 범용 프로그래밍 기능을 갖고 있다. NPU는 MAC 유닛을 격자로 깔아 둔 구조(시스톨릭 배열 등)로, 데이터가 이웃 유닛으로 흘러가며 곱하고 더한다.
- **데이터 이동 줄이기**: 계산보다 메모리에서 데이터를 가져오는 데 전력이 훨씬 많이 든다. NPU는 가중치와 중간값을 칩 안 메모리에 두고 재사용하도록 설계한다.
- **낮은 정밀도**: 추론은 32비트 실수 대신 8비트 정수(INT8)나 16비트로도 충분한 경우가 많다. 비트 수가 작으면 회로가 작아지고 같은 면적에 MAC 유닛을 더 넣을 수 있다.
- **전력**: 휴대폰은 배터리로 돌아간다. 같은 AI 기능을 GPU보다 훨씬 적은 전력으로 처리하는 것이 NPU의 존재 이유다.

정리하면 GPU는 "병렬 계산 범용기", NPU는 "신경망 MAC 전용기"다. 구글 TPU, 애플 Neural Engine, 퀄컴 Hexagon NPU가 예다.

<a id="q09"></a>
### 09. 연산 횟수는 왜 N²이고, Big-O는 무엇인가?

N×N 격자에는 칸이 N × N = N²개 있다. MAC은 모든 칸에서 곱셈 1번, 덧셈 1번을 하므로 연산 횟수가 N²에 비례한다. 코드로 보면 `for`가 두 겹이고 각각 N번 돈다.

**Big-O 표기법**은 입력 크기 N이 커질 때 실행 시간(또는 메모리)이 **어떤 모양으로 늘어나는지**만 나타낸다. 상수 배와 작은 항은 지운다.

| 표기 | 의미 | N이 2배가 되면 | 예 |
| --- | --- | --- | --- |
| O(1) | 크기와 무관 | 그대로 | 리스트에서 인덱스로 값 하나 읽기 |
| O(log N) | 로그 | 조금 늘어남 | 정렬된 목록에서 이진 탐색 |
| O(N) | 비례 | 2배 | 리스트 한 번 훑기 |
| O(N log N) | | 2배보다 약간 더 | 좋은 정렬 알고리즘 |
| O(N²) | 제곱 | 4배 | 이 미션의 MAC, 이중 반복문 |
| O(2ᴺ) | 지수 | 엄청나게 | 모든 부분집합 검사 |

이 미션의 실측에서 N을 2배로 늘릴 때마다 시간이 약 4배가 됐다([README 5.2](README.md#52-시간-복잡도-분석)). 판정 1건에 필터 2개를 쓰면 2N²번이지만 Big-O에서는 상수 2를 지워 O(N²)로 쓴다.

<a id="q10"></a>
### 10. 공간 복잡도는 무엇인가?

시간 복잡도가 "얼마나 오래 걸리나"라면, 공간 복잡도는 **"메모리를 얼마나 쓰나"** 를 같은 Big-O로 나타낸 것이다.

- 이 미션에서 패턴과 필터를 저장하려면 N×N 배열이 필요하므로 **O(N²)**.
- MAC 계산 자체가 추가로 쓰는 메모리는 누적값 `total` 하나라서 **O(1)**.

1000×1000이면 칸 100만 개다. Python의 `float`은 객체라서 칸마다 대략 24바이트 + 리스트 포인터 8바이트가 들어 배열 하나에 약 32 MB가 된다. 같은 데이터를 C 배열이나 `array` 모듈로 저장하면 8 MB다. 시간뿐 아니라 메모리 표현 방식도 성능에 영향을 준다.

<a id="q11"></a>
### 11. 정규화는 정확히 무엇인가?

"정규화(normalization)"는 분야마다 뜻이 조금 다르지만 공통점은 **제각각인 것을 하나의 기준 형태로 맞추는 것**이다.

| 분야 | 뜻 | 예 |
| --- | --- | --- |
| 통계·머신러닝 | 값의 범위나 분포를 맞춤 | Min-Max(0~1로), Z-score(평균 0, 표준편차 1로) |
| 벡터 | 길이를 1로 맞춤 | 코사인 유사도에서 벡터를 길이로 나눔 |
| 데이터베이스 | 중복을 없애도록 표를 나눔 | 제1, 2, 3 정규형 |
| 문자열·라벨 | 같은 뜻의 여러 표기를 하나로 | `'+'`, `'cross'`, `'Cross'` → `Cross` |

통계에서 본 것은 첫째 줄이고, 이 미션의 "라벨 정규화"는 마지막 줄이다. 영어로는 standardization이라고도 해서 "표준화"라고 함께 쓴다. 이 미션에서 정규화가 필요한 이유는 `data.json`이 정답을 `'+'`, `'x'`로, 필터를 `'cross'`, `'x'`로 다르게 적기 때문이다. 입구에서 한 번 표준 라벨로 맞추면 그 뒤 코드는 표기 차이를 신경 쓰지 않는다.

<a id="q12"></a>
### 12. 부동소수점의 '부동'은 무엇이 움직이지 않는다는 뜻인가?

반대다. 부동(浮動)은 **"떠서 움직인다"** 는 뜻이다(움직이지 않는다는 不動이 아니다). 영어 floating point, 즉 **소수점이 떠다니는** 수 표현이다.

과학적 표기법처럼 수를 "유효숫자 × 2의 지수"로 저장하고, 지수를 바꿔 소수점 위치를 옮긴다.

```text
값 = 부호 × 1.가수(2진수) × 2^지수
64비트(double): 부호 1비트 + 지수 11비트 + 가수 52비트
```

소수점 위치가 고정된 **고정소수점(fixed point)** 과 대비되는 이름이다. 소수점을 띄워 두기 때문에 아주 큰 수와 아주 작은 수를 같은 64비트로 표현할 수 있다.

오차가 생기는 이유는 "소수를 표현할 수 없어서"라기보다 **2진수로 유한하게 끝나지 않는 소수가 있어서**다. 10진수에서 1/3 = 0.333…이 끝나지 않듯, 2진수에서는 0.1이 `0.0001100110011…`로 끝나지 않는다. 52비트에서 잘라 반올림하므로 0.1은 실제로 0.1000000000000000055511…이 되고, 이것을 여러 번 더하면 오차가 쌓인다.

```python
>>> 0.1 + 0.2
0.30000000000000004
>>> sum([0.1] * 9)
0.8999999999999999
```

정밀함이 중요한 분야에서 실제 사고로 이어진 예가 있다. 1991년 걸프전 패트리어트 미사일 시스템은 0.1초 단위 시간을 2진수로 저장한 오차가 100시간 동안 쌓여 약 0.34초가 어긋났고, 그 결과 요격에 실패했다. 질문에서 들었던 "무기 체계" 사례가 이것이다. 그래서 돈 계산에는 `decimal`, 정확한 분수에는 `fractions`를 쓰고, 실수 비교에는 허용오차를 둔다.

<a id="q13"></a>
### 13. 허용오차를 왜 입실론이라고 부르나?

입실론(ε)은 그리스 문자이고, 수학에서 오래전부터 **"아주 작은 양수"** 를 나타내는 기호로 쓰였다(극한의 ε-δ 정의). 그 관례가 컴퓨터로 이어져 "이만큼 차이는 무시한다"는 작은 허용 범위를 ε, epsilon이라 부른다. 허용오차의 영어는 tolerance이고, epsilon은 그 값을 부르는 이름이라고 보면 된다.

비슷한 이름으로 **기계 입실론(machine epsilon)** 이 있다. 1.0과 그다음 표현 가능한 수의 차이로, 64비트 실수에서는 약 2.22×10⁻¹⁶이다(`sys.float_info.epsilon`). 이 미션의 동점 오차(1.1×10⁻¹⁶ ~ 2.7×10⁻¹⁵)가 바로 이 크기 수준이다. 비교 기준 1e-9는 이보다 훨씬 크게 잡은 실무용 허용오차다.

<a id="q14"></a>
### 14. '비교 정책'이라는 말이 필요한가? 다른 기준은 없나?

거창해 보이지만 "정책"이라는 말이 맞다. 실수 비교에는 정답이 하나가 아니라 **선택**이 있고, 그 선택을 문서로 정해 두고 모든 곳에서 똑같이 쓰자는 뜻이기 때문이다. 같은 프로그램 안에서 어떤 곳은 `==`, 어떤 곳은 1e-9, 어떤 곳은 1e-6으로 비교하면 결과가 경우마다 달라진다.

MAC 대신 다른 방법을 찾자는 질문과는 별개다. MAC 점수가 나온 **뒤**, 두 점수를 어떻게 비교할지의 문제다. 고를 수 있는 기준은 여러 가지다.

| 기준 | 식 | 언제 |
| --- | --- | --- |
| 정확히 같음 | `a == b` | 정수, 또는 오차가 없다고 보장될 때만 |
| 절대 허용오차 | `abs(a - b) < ε` | 값의 크기가 비슷한 범위일 때. 이 미션의 정책 |
| 상대 허용오차 | `abs(a - b) < ε × max(|a|, |b|)` | 값이 아주 크거나 작을 수 있을 때. 1e12와 1e12+1을 같다고 봄 |
| 둘을 함께 | `math.isclose(a, b, rel_tol, abs_tol)` | 파이썬 표준 함수. 일반적으로 가장 안전 |
| 반올림 후 비교 | `round(a, 9) == round(b, 9)` | 간단하지만 경계값에서 어긋날 수 있음 |
| 오차 없는 수 사용 | `decimal.Decimal`, `fractions.Fraction` | 돈, 정확한 비율. 느림 |
| 정수로 바꿔 계산 | 0.1 → 1로 스케일 | NPU의 INT8 양자화처럼 처음부터 오차를 없앰 |

동점 처리도 정책이다. 이 미션은 모드 1에서 "판정 불가", 모드 2에서 "UNDECIDED = FAIL"로 정했다. "동점이면 Cross 우선"처럼 정할 수도 있지만, 그러면 데이터 문제를 숨긴다.

<a id="q15"></a>
### 15. 실패 원인 세 갈래는 각각 어떻게 진단하고 고치나?

| 갈래 | 생기는 상황 | 진단 방법 | 개선 |
| --- | --- | --- | --- |
| 데이터/스키마 | 키 이름 규칙 위반(`size5_1`), 라벨 표기 차이(`'+'` vs `'cross'`), 행·열 개수 불일치, 문자열 숫자(`"1"`), 필수 키 누락, 맞는 크기의 필터 없음 | 계산 **전에** 모양·타입·키를 검증해 어디가 틀렸는지 메시지로 남긴다 | 데이터 수정, 정규화 규칙 추가, 검증 강화 |
| 로직 | 행·열 인덱스를 바꿔 씀, 누적 변수를 반복 안에서 초기화, 필터를 잘못 고름, 비교 부호 반대 | 손으로 계산할 수 있는 작은 예(3×3 십자가·X)로 기대값과 비교, 다른 케이스는 맞는지 확인 | 코드 수정, 단위 테스트 추가 |
| 수치 비교 | 수학적으로 같은 두 점수가 부동소수점 오차로 1e-16만큼 다름 | 두 점수의 차이를 출력해 본다. 차이가 1e-15 수준이면 오차, 0.1 이상이면 실제 차이 | 허용오차 비교 정책, 필요하면 정수·Decimal 계산 |

순서가 중요하다. 스키마를 먼저 걸러야 로직 문제와 섞이지 않고, 로직이 맞다고 확인된 뒤에야 남은 차이를 수치 문제로 볼 수 있다. 이번 `data.json`의 FAIL 3건은 이 순서로 앞의 두 갈래를 배제하고 수치 비교(동점)로 결론 냈다([README 5.1](README.md#51-실패-원인-분석)).

<a id="q16"></a>
### 16. 왜 N×N 정사각형 2차원 패턴을 쓰나?

이 미션에서는 단순화를 위해서다. 십자가와 X는 가운데를 기준으로 대칭인 모양이라 홀수 N의 정사각형에 딱 맞는다(가운데 칸이 하나 있어야 십자가의 교차점과 X의 교차점이 생긴다). 행과 열 크기가 같으면 크기를 숫자 N 하나로 부를 수 있어서 `size_N` 키 규칙과 N² 분석도 간단해진다.

실제 AI에서는 꼭 정사각형일 필요가 없다. 이미지는 1920×1080처럼 직사각형이고 색상 채널(RGB)까지 있어 3차원이다. 다만 필터는 3×3, 5×5 같은 작은 정사각형을 많이 쓰고, 이 필터를 큰 이미지 위에서 옮기며 MAC을 한다. 이 미션은 패턴 크기와 필터 크기가 같아서 한 번만 겹쳐 보는 가장 단순한 경우다.

<a id="q17"></a>
### 17. 특정 위치를 저장하려면 좌표가 필요한가?

그렇다. 2차원 배열에서는 **(행, 열)** 두 숫자가 좌표 역할을 한다. 파이썬 리스트의 리스트라면 `grid[행][열]`로 읽고 쓴다. 이 미션의 `Grid` 클래스도 `get(r, c)`, `set(r, c, v)`로 같은 일을 한다.

메모리는 사실 1차원 주소의 연속이라서, 2차원 좌표는 결국 1차원 위치로 바뀐다. 행 우선(row-major) 순서로 펴면 다음 공식이 성립한다.

```text
1차원 인덱스 = 행 × N + 열
(1, 2) in 3×3 → 1 × 3 + 2 = 5
```

보너스 과제의 1차원 최적화가 이 원리를 쓴다. 좌표 두 개로 두 번 찾아가는 대신 인덱스 하나로 한 번에 찾아가므로 칸당 비용이 줄었다(실측 약 17~39% 단축).

### 18. 평가 인터뷰 대비: 새 라벨, 1000×1000, CPU vs NPU 병목

**새 라벨 `'o'`(동그라미)가 추가된다면.** 바깥에서 안쪽으로 확장한다.

1. 정규화: `LABEL_ALIASES`에 `'o': 'Circle'` 추가(표기 하나만 고치면 되는 것이 정규화를 분리한 이점).
2. 데이터: `filters`의 각 `size_N`에 `o` 필터가 있는지 검증 대상에 포함.
3. 판정: 두 점수 비교(A/B)를 **여러 점수 중 최댓값**으로 일반화하고, 1등과 2등의 차가 ε보다 작으면 UNDECIDED.
4. 출력: 케이스마다 라벨별 점수를 반복 출력하도록 고정 문구(Cross 점수, X 점수)를 바꿈.
5. 테스트: 기존 6개 케이스가 그대로 통과하는지 먼저 확인하고, `o` 패턴·`o` 필터 누락·세 라벨 동점 케이스를 추가.

**1000×1000 패턴을 처리한다면.** 칸이 100만 개다.
- 시간: 실측 칸당 약 0.05 µs면 MAC 1번 50 ms, 필터 2개면 100 ms. 한 번은 괜찮지만 이미지 위 여러 위치·여러 필터로 반복하면 순수 Python으로는 감당이 안 된다.
- 메모리: 파이썬 `float` 객체 리스트로 배열 하나에 약 32 MB, 패턴·필터 3개면 100 MB에 가깝다. JSON 파일 자체도 수십 MB이고 `json.load`가 통째로 읽는다.
- 우선 적용할 최적화: ① 1차원 연속 배열(`array('d')`)로 메모리와 접근 비용 줄이기, ② 값이 0인 칸 건너뛰기(이 필터들은 대부분 0이라 효과가 큼, 희소 연산), ③ 정수로 스케일해 부동소수점 오차와 비용을 함께 줄이기, ④ 그다음 단계로 벡터화 라이브러리나 병렬 하드웨어 사용(이 미션에서는 금지).

**CPU 직렬 vs NPU 병렬, 병목은 어디인가.** MAC 하나하나는 서로 독립이라 원리상 동시에 할 수 있다(덧셈 순서만 정하면 됨). CPU는 코어 수가 적어 이 독립성을 거의 못 쓰고, N²번을 한 줄로 처리하므로 **계산 자체**가 병목이 된다. NPU는 MAC 유닛 수천 개로 계산을 한꺼번에 하므로 계산은 빨라지지만, 이번에는 그 유닛들에 데이터를 제때 공급하는 **메모리 대역폭(데이터 이동)** 이 병목이 된다. 그래서 NPU 설계는 가중치를 칩 안에 두고 재사용하며 데이터 이동을 줄이는 데 집중한다. 마지막 누적 합산 단계도 완전히 병렬화하기 어려워 트리 모양으로 나눠 더하는(리덕션) 방식을 쓴다.
